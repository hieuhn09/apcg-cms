## What This Repo Is

A single **multi-tenant Payload CMS** that centrally manages several content/news websites
(publications, called *tenants*): one admin, one Postgres database, one media store. Content
engines push drafts in over HTTP; thin website frontends pull **published** content out over HTTP
via a per-tenant read token. It replaces an earlier model where every website embedded its own
Payload CMS and database (`README.md:1-10`).

## How This File Works (the `all-*.md` Convention)

Every `process/context/` subdirectory has one `all-*.md` entrypoint acting as an attachable quick
router for that domain. This root file (`all-context.md`) is the top-level router. Each context
group has its own `all-{group}.md` entrypoint.

**The pattern:**

```
process/context/
  all-context.md                      <-- THIS FILE: root router
  database/
    all-database.md                   <-- group router for schema/tenant-model/migrations
  integrations/
    all-integrations.md               <-- group router for API surface/auth
  planning/
    all-planning.md                   <-- group router for plan-shape calibration
  tests/
    all-tests.md                      <-- group router for verification (no test framework exists)
```

**How agents use it:**

1. Read `all-context.md` first (this file)
2. Find the relevant context group in the routing tables below
3. Read that group's `all-{group}.md` entrypoint
4. Only then load a specific deeper file (code, `docs/*.md`, or a plan) that the group points to

This layered routing keeps context windows small. Never load the whole `process/context/` tree.

**Every `all-{group}.md` contains:**

- Scope (what the group covers and does NOT cover)
- Read-when rules
- Quick routing to deeper files
- Source paths
- Update triggers

## Context Group Lifecycle

Context groups are **durable knowledge domains**, not feature folders.

Create a group when:

- a topic has 3+ durable docs
- a single doc exceeds roughly 800 lines with separable subtopics
- multiple agents repeatedly need only one slice of a large context file
- the topic maps to a stable operational domain

Do not create a group when:

- the content is a temporary report
- the content is a plan or execution artifact (those live in `process/general-plans/` — this repo
  has **no dedicated feature-folder structure yet** — there is no `features` directory under
  `process/` on disk; every plan currently lives under `process/general-plans/`,
  see **Current Active Work** below)
- the topic is feature-specific

Move/split one group at a time. Use `all-{group}.md` entrypoints. Run the `vc-audit-context` skill
after every context organization change.

## Key Patterns and Conventions

**Two data-access lanes, chosen by caller type.** Human editorial traffic (Payload admin +
Console) goes through the Payload Local API so hooks/access-control/versions/localization all run.
Machine and public traffic (engine intake/translation, `/api/public/*`, cron) has no Payload
session, so it MUST go through `src/lib/scoped.ts` (`scopedFind`/`scopedCreate`/`scopedUpdate`,
which merge an explicit tenant filter into every query). The Console's dashboard *reads* additionally
bypass even the Payload Local API via a separate read-only Drizzle client, for aggregation speed —
its *writes* still go through Payload. Full detail: `process/context/database/all-database.md`
§Two data-access lanes.

**Two independent, differently-shaped auth mechanisms**, neither generalizing to the other: a
human Payload session (reused as-is by both `/admin` and `/console`) vs machine bearer tokens
(engine token and per-tenant public read token are *two different* bearer schemes, and both resolve
to exactly **one** tenant per call). **Updated 2026-09-24:** a third, separate machine credential
now reads across tenants — `ContentEngines.hubRead` + `authenticateHubEngine`/`narrowHubTenants`
(`src/lib/hub-auth.ts`), used only by the internal, read-only `/api/hub/*` routes (APCGHub P4:
CMS-1 `GET /api/hub/articles`, merged in #18; CMS-2 `GET /api/hub/tenants` + `GET /api/hub/taxonomy`
+ search/pillar/views on `/api/hub/articles`, draft PR #19). Engine and public tokens still resolve
to one tenant; the Console's `tenantScope()` is still human-session-only; cross-tenant **writes** do
not exist anywhere — **updated 2026-09-25:** one narrow exception now exists, the CMS-3 route
`POST /api/hub/articles/{id}/status` (one article, one tenant, `workflowStatus` only: hide =
`published → archived`, republish = `hidden|archived → published`), gated by a separate
`ContentEngines.hubWrite` flag checked in `src/lib/hub-write-auth.ts` (`hub-auth.ts` stays read-only). Anyone adding a new cross-tenant read should extend the `/api/hub/*` pattern
(allowlist `select` + sanitize + `depth: 0`, empty-param semantics, merge ordering) — full detail:
`process/context/integrations/all-integrations.md` §Cross-tenant reads.

**Dual status model on `Articles`:** `_status` (Payload's native draft/published, from its
versions engine) is independent of `workflowStatus` (this repo's own 7-value editorial lifecycle).
**Public visibility is gated on `workflowStatus === "published"` alone** — `_status` is
deliberately not filtered, because ~3,300 imported articles sit at `_status:"draft"` +
`workflowStatus:"published"` and are correctly live. Any new read surface must key off
`workflowStatus`. Full detail: `process/context/database/all-database.md` §The dual article-status
model.

**Relationship population can leak fields that `access.read` would otherwise block.**
`overrideAccess: true` (used by every scoped machine/public query) bypasses a collection's own
`access.read` for the document being fetched, but a *populated relationship* on that document is a
separate mechanism (`defaultPopulate`) that is NOT bypassed the same way — so a collection with a
secret/PII field that gets related-to from a public document needs an explicit `defaultPopulate`
allow- or deny-list, or the secret leaks through the relationship. Three collections
(`ContentEngines`, `Users`, `Tenants`) already carry this guard for exactly this reason (a real,
found-and-fixed production leak — see `process/general-plans/active/cms-cost-remediation_09-09-26/`).
Any new relationship to a secret-bearing collection needs the same treatment; nothing enforces it
automatically. Full detail: `process/context/integrations/all-integrations.md` §Security patterns.

**Content-engine intake is a cross-repo wire contract, not a Payload-native feature.** The JSON
shape at `POST /api/engine/intake` mirrors what the separate `content-engine` repo's clients
already send (named in the route's own docstring). Same for `/api/public/*` toward the five
frontend repos. Changing either contract needs cross-repo coordination, not just a local review.
Full detail + field list: `docs/08-content-engine-integration.md`,
`process/context/integrations/all-integrations.md`.

**`ActivityLog` is append-only and best-effort.** `logActivity()` (`src/lib/activity.ts`) never
throws into its caller — a logging failure must never break the write it is annotating. The
collection's own `access.create` is hardcoded `false`; the only legitimate writer is
`logActivity()`'s internal `overrideAccess: true` call.

**Comment-driven "why," heavily.** Nearly every non-trivial file in `src/lib/` and
`src/collections/` carries a substantial block comment documenting a real past incident or
trade-off (a PII leak, a billing-driven gzip decision, an R2 key-mismatch outage, a migration
hardening pass). Reading the top-of-file comment before editing is usually necessary, not optional
— several of the findings in this context file's groups came directly from those comments plus
independent verification, not from guessing.

**Naming:** kebab-case files; PascalCase Payload collection files/exports (`Tenants.ts` exports
`Tenants`); collection **slugs** are mostly camelCase (`tenants`, `activityLog`,
`translationJobs`) with one kebab-case exception (`content-engines`) — worth knowing when writing a
`where` clause or a `collection:` string, not worth "fixing." Import aliases: `@/*` → `src/*`,
`@payload-config` → `payload.config.ts` (declared in **both** `tsconfig.json` and
`next.config.ts`'s webpack alias — keep both in sync if it ever moves).

## Linting, Type-checking, and Testing

- `npm run typecheck` (`tsc --noEmit`, strict) and `npm run lint` (`next lint`) are the only two
  automated quality commands in this repo.
- **There is no automated test framework** — no `test` script in `package.json`, and no
  vitest/jest/playwright/mocha dependency anywhere in `package.json`. Do not assume one exists or
  invent a `npm test` command.
- **There is no CI configuration** — `.github/` does not exist in this repo at all (confirmed
  directly, not just an empty `workflows/`). Nothing runs lint/typecheck automatically on push or PR
  today.
- **Verification pattern used in this repo's own plans**, per `process/general-plans/active/cms-cost-remediation_09-09-26/`
  (a completed, well-documented VALIDATE→EXECUTE→EVL cycle): typecheck + lint locally, then **live**
  verification against a Preview/Production deploy — curl probes against real routes, direct SQL/
  admin-panel counts, and Vercel Observability dashboard reads. Design any new validate-contract's
  test gates around this shape (typecheck/lint as the cheap automated tier; a manual/live probe tier
  for anything behavioral), not around a test-runner command that does not exist.
